# 2026-11-02 速度问题诊断

依据用户本次提供的两份20261101工程包和板端计时；本次没有连接AX7021B、修改Overlay或重启预览服务。

## 已证实的原因

安全帽单图总耗时22,754.64ms，其中预处理121.45ms、模型22,619.54ms、后处理13.64ms。模型占99.4%；加载329.45ms发生在初始化，不是每帧都发生。后台同进程反复调用仍有24–30秒模型时间，排除每次重新加载作为主要原因。

实际平台ARMv7、Python3.10.4、OpenCV4.5.4，没有ONNX Runtime。A已正确把640模型拆为卷积检测头及NumPy解码以解决ONNX算子兼容性。这是兼容适配，不减少卷积计算。640×640的YOLOv8n在该ARM CPU/OpenCV后端上执行卷积，是当前已测主要瓶颈。未取得板端OpenCV构建信息，不能擅自断言NEON未启用或库编译错误。

后台源码已经把预览、推理分线程，模型只初始化一次，最新结果容量1，没有把Haar和安全帽串行执行；不重复建议已完成的异步重构。4次检测、约110.7秒总运行内，检测约0.036fps；预览各记录窗口约5–9fps。预览和检测共享CPU，CPU记录接近两核满载，能解释与独立推理相比部分模型耗时增大，但需要同条件实测才能分离具体争用成本。历史小图的40–55秒年龄不是模型又额外计算了55秒，而是源图年龄。

当前安全帽模式pl_gray_used=false，与代码一致；PL灰度IP不会自动加速YOLO卷积。不能用更换灰度IP、延长队列或刷新Notebook解决22秒forward。也不能用摄像头30fps宣称检测30fps。

人脸3–4秒的最新工程不在这两包内，无法确认其当前参数与分阶段耗时。旧Haar默认最长边640、scaleFactor1.1，确实存在可减少的搜索开销；本轮提供独立480配置及对照，但不把旧约0.88秒记录冒充当前3–4秒根因测量。

## 修改内容与取舍

1. 提供相同学习权重的320模型和兼容原始头导出，候选点从8400减至2100。解码尺寸不再写死，锚点/步长/DFL投影在初始化缓存。缓存只减少少量解码开销，不能把它称为22秒瓶颈修复。
2. 保留640原始头配置作为质量基准；默认仍是board640，禁止无提示自动降为320。board320只有显式选择才启用。
3. 提供640本地NCNN后端路线，目标是在保留输入分辨率和权重的情况下换用更适合ARM的推理实现。是否可用、PC数值与速度、板端是否实测以随包报告为准；未安装NCNN时明确报错，不悄悄回退成颜色演示。
4. 人脸FastFaceDetector采用480搜索、保持scaleFactor1.1；现有PL输入仍由640准备器处理，再在PS缩放灰度用于Haar，保留原图坐标。避免为提速擅自改变DMA/视频IP输入长度。是否启用仍需对照漏检率。

320相对640每层空间面积约1/4，不代表板端实测一定快4倍，更不代表能达到实时。PC结果、板端推测和实际板端验收必须分开。

## 板端验证

先用原有“正常停止”按钮等后台安全退出，保持原Overlay和显示资源规则，不强杀占有VDMA缓冲区的进程。独立模型测速脚本不打开相机、不访问DMA、HDMI或寄存器：

```bash
/usr/local/bin/pynq-a-python2025 board_benchmark.py --image /path/to/complete_head.jpg --profiles board640 board320 --repeats 3 --output board_results.json
```

安装并验证NCNN后增加ncnn640对照。应先查依赖是否可导入，按实际ARMv7/Python3.10环境准备兼容构建；Windows的ncnn wheel不能复制上板。不要直接升级已经稳定的板端OpenCV或PYNQ。

以相同输入比较模型加载、暖态forward、完整处理、RSS和输出状态，再与预览并发测一次。只有这个新板端结果才能回答实际缩短到几秒。相同图像的框必须与640基准核对；降分辨率特别需要检查小安全帽和远处人员漏检。
